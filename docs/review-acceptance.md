# Exact-artifact review acceptance

HSDLC-075 (implemented 2026-10-15): review is an explicit, local operation, separate
from worker execution, scoped commits and source integration. This slice adds
a shared Python service and CLI commands; it does not change MCP execution
schemas or add automatic reviewer/model calls.

## Selection and decisions

`hybrid-sdlc review status RUN_RECORD --repo-root REPO --json` inspects the
selected persisted run and its current review. `RUN_RECORD` is the run-record
artifact path returned by execution, relative to the source repository or an
absolute path within that run's validated private artifact directory. No
directory scans, arbitrary evidence imports or guessed latest-run selection.

## CLI workflow

First inspect the selected run and its private `review_patch` against the task
contract. Use the actual `artifacts.run_record` path returned by execution:

```sh
hybrid-sdlc review status .hybrid_sdlc/runs/run_ID.json --repo-root . --json
```

Status returns the baseline commit, SHA-256 of the full raw patch, and current
review revision. A missing review starts at revision `0`; it is not accepted.
Only `current: true` together with `judgment: "accepted"` represents a current
acceptance. Invalid or unsupported selected artifacts can return a structured
policy error instead; neither an error nor a missing/stale record authorizes
integration.
Copy those identities only after inspecting that exact candidate. In the next
example, set `BASELINE` and `PATCH_SHA256` to the values from status, replace
`run_ID`, choose your configured test profile, and use the displayed revision:

```sh
hybrid-sdlc review record .hybrid_sdlc/runs/run_ID.json --repo-root . --decision accepted --reviewer-kind human --reviewer reviewer-one --expected-baseline "$BASELINE" --expected-patch-sha256 "$PATCH_SHA256" --expected-revision 0 --test-profile unit --json
hybrid-sdlc review status .hybrid_sdlc/runs/run_ID.json --repo-root . --json
```

An acceptance request executes the named test profile in a new isolated
checkout. Check the returned judgment and subsequent status: failed verification
is `blocked`, not accepted. A rejected or blocked judgment does not need
`--test-profile`. For a model reviewer, use `--reviewer-kind model`, keep the
reviewer's label in `--reviewer`, and supply its claimed identifier separately
with `--reviewer-model`. This does not invoke a model or authenticate its identity.

Changing an existing decision requires its current revision, not `0`. On a
revision conflict, reload status and reconsider the candidate; do not blindly
retry with a larger number. There is no corresponding MCP review tool in this
slice. The existing five execution/job tools keep their contracts.

## Record identity

`hybrid-sdlc review record RUN_RECORD` requires the repository root, a decision
(`accepted`, `rejected`, `blocked`), reviewer identity/kind, expected baseline,
expected full patch SHA-256 and expected review revision (zero before the first
record). Acceptance additionally requires a named test profile. Model reviewers
must provide a model identifier. No free-form conversation, raw test output,
credentials or member data belongs in reviewer labels.

The strict versioned review record binds the run ID, actual baseline, SHA-256 of
the entire raw patch, digest of the persisted run record, reviewer provenance,
decision, revision and controller-generated test evidence. Legacy run results
remain readable; never trust their older `final_diff.diff_hash` as a raw patch
digest. Missing/unsupported artifacts produce no current acceptance.

## Independent test evidence

An accepted request requires successful worker execution and a fresh isolated
verification checkout at the recorded baseline, with the exact patch applied
using Git's safe binary-patch application. The source repository must still
have that baseline as HEAD; moving HEAD makes the prior acceptance stale. No
source checkout changes, commits, inference requests or integration are made.

The controller resolves and runs the named profile, not a caller-supplied
`passed: true` value. It records profile identity/fingerprint, observed exit,
timeout/cancellation/truncation metadata and duration, without raw output.
Verification failures include a bounded category rather than exception text or
captured test logs. A successful command exit alone does not prove acceptance;
read the returned judgment and current status.
The replayed candidate is snapshotted before and after tests. Exported changes
caused by tests invalidate verification rather than being silently accepted.
Where a task policy exists, recheck its pinned scope on the replayed candidate;
legacy runs without a policy do not gain a scope-validation claim.

Different valid patch encodings need not have identical regenerated bytes.
Bind the original raw patch digest separately from the replay snapshot and
verify that the latter remains unchanged during testing. Missing tools,
inapplicable/unsafe patches or failed/changed test candidates cannot produce
acceptance. A failed acceptance check is recorded as blocked with its observed
verification outcome, not falsely accepted. Rejected/blocked human judgments
do not need to execute tests.

## Storage, reads and concurrency

Use the validated run's existing private `.hybrid_sdlc` artifact root for review
metadata, with bounded reads, strict versions/fields, safe non-link paths and
atomic writes. Keep verification evidence separate and bind its digest in the
review record. Run-record and patch digests hash the original full bytes. The
receipt digest hashes sorted compact JSON with its own `sha256` field zeroed;
reads also require the entire persisted receipt to match the embedded receipt.
Evidence references are confined to toolkit-owned artifacts and
validated against the selected run, baseline and patch; arbitrary external
files are not trusted as evidence. Review/replay artifacts share the existing
artifact retention boundaries. Cleaned or missing referenced evidence means no
current acceptance, not an opportunity to recreate a claimed passing receipt.
Standard artifact cleanup covers metadata under its selected `.hybrid_sdlc`
root and skips locked files. It does not recursively remove external worker or
verification worktrees; those retain the existing explicit, known-artifact
cleanup boundary. Removing referenced evidence invalidates acceptance.

Serialize updates under a per-review lock shared with retention. Check the
expected revision under that lock and hold it across verification and
persistence; stale or concurrent submissions fail explicitly. Readers validate current artifacts and
evidence, reporting missing, invalid or stale review state rather than exposing
a stored `accepted` label as a current authorization. Reads do not modify state.

## Trust boundary

Reviewer identity and model provenance are recorded claims, not authentication.
Label known same-model review explicitly; unknown worker/reviewer provenance
must not be upgraded to a claim of independent model judgment. Independently
executed tests are execution evidence, not proof of product correctness.
Local records and hashes detect inconsistencies, not an owner who rewrites all
related files consistently. Trusted repository commands and same-user access
remain outside an OS sandbox. No automatic merge or integration follows from
any review decision.
